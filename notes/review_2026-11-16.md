# Project review memo (2026-11-16)

Reviewed: repository skeleton, `docs/phase_task_guide.pdf`, Notion project page.
This memo was written by an AI assistant (Claude). It may be wrong; check each point against real data in the W2 small-scale run.

## 1. Summary

- The project can be hand-coded. It needs five scripts, roughly 400–600 lines in total (estimate).
- The core of the project is not the code but the human-made artifacts: codebook, probes, gold labels.
- Recommended workflow: pseudo-code (comments) → hand-written code → AI as reviewer only.

## 2. Workflow

1. Each file in `src/` contains only function names, inputs/outputs and step comments. No implementation.
2. Turn the comments into code one step at a time.
3. After finishing each function, run the matching check in `notes/verification_guide.md`.
4. Use AI only to interpret error messages, answer library-usage questions, and look for bugs in code you have already written.

## 3. Difficulty by file (assuming basic Python/pandas)

| File | Difficulty | Hard part |
|---|---|---|
| `m0_rules.py` | Easy | Rule order; must match the codebook's decision order |
| `run_llm.py` | Easy | Keeping only the codebook block different across conditions; logging |
| `metrics.py` | Medium | Bootstrap intervals; handling rare classes |
| `collect_lda.py` | Medium | Pagination, rate limits, resuming after an interruption |
| `extract_sentences.py` | Hardest | Defining a "sentence"; LDA descriptions are often not sentences |

## 4. Where not to use AI

Evaluating an LLM with items or rules written by an LLM undermines measurement validity. Make these by hand:

- The 40 probes
- Definitions, clarifications and examples in codebook v0.1 and v1.0
- Gold labels and re-labels
- Error-category definitions and error coding
- M0 rules

State the scope of AI use in one paragraph in the report's methods or limitations section. Log each use with its date in Research Journal.

## 5. Design points to check first

### 5.1 Are there enough boundary cases? (largest risk)

- LDA activity descriptions are often lists of noun phrases such as "H.R. 1234, XX Act; issues related to ...". Phrases like "supported with amendments" or "expressed concerns" may be rare.
- The plan counts pattern hits in W4. Move this to W2, right after collection.
- Fix the decision rule in advance. Example: if the five patterns together yield fewer than 60 hits, change the design.
- Fallbacks: widen the filing years, broaden the patterns, or rebuild around probes with fewer real boundary cases. Record whichever you choose in Research Journal.

### 5.2 Circularity in RQ4

- If real boundary cases are found with regular expressions and M0 classifies with the same expressions, M0 has a built-in advantage.
- Fix: keep extraction patterns broad (recall-oriented) and write M0 rules separately and narrowly. Keep the two pattern lists in different files and report both.
- Also report M0 vs LLM on the random sample of 100, which gives an unbiased baseline.

### 5.3 Rare classes and sample size

- The random sample of 100 is likely to be mostly MENTION. OPPOSE and UNCLEAR may have only a few items.
- The test split is 60% of real items, roughly 100. Bootstrap intervals for macro-F1 will be wide.
- Fix: report per-class counts in every table. Decide in `tests_spec.md` how macro-F1 is computed when a class has zero gold items in a split.

### 5.4 Blanks to fill

- `notes/tests_spec.md`: every threshold and the minimum reliability. Fix them before running. The guide's starting point is Test I ≥ 0.95, Tests II and III ≥ 0.80.
- Full citation for Kim et al. (2025) and exactly what that study gave the model. Condition A must match it.
- Current LDA API address and rate limits. Check the official documentation before writing the collector.
- `codebook/codebook_v0.1.md`: every field for all five classes.

### 5.5 Smaller points

- A sentence citing several bills becomes one row per (sentence, bill) pair. If rows from the same sentence end up in both dev and test, that is leakage, so split by sentence.
- Check by string comparison that codebook examples, probes and real items do not overlap.
- Even at temperature 0 with a fixed seed, outputs can change if the Ollama version or model file changes. Record the model ID from `ollama list` for every run.
